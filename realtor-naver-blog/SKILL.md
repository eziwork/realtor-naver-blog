# 검색 의도와 문의 전환을 설계하는 매물 블로그 (내장 브라우저 전용)

매물 한 건당 글 한 편. Codex가 분석·전략·문체·원고·화면 검수를 수행하고, 코드는 파일·출처 연결·전략 확정·전송 상태를 검증한다. 각 단계에서 짧게 진행 상황을 알린다.

**브라우저는 Codex 내장 브라우저 하나만 쓴다.** 매물 수집·로그인·입력·사진 업로드·저장·재열람 모두 내장 브라우저(Browser 플러그인 `tab.playwright` API)로 한다. 셸에서 브라우저를 띄우지 않고, Playwright·Chromium을 설치하지 않는다. 내장 브라우저를 쓸 수 없으면 다른 브라우저 자동화로 몰래 전환하지 말고 BLOCKED로 보고한다.

## 지켜야 할 계약

- **사실과 가설 분리.** 가격·면적·거리·시설·이용 가능·수익·방문 경험을 절대 지어내지 않는다. 확인 필요 항목은 원고 작성 전에 스킬 사용자에게 Codex 질문으로 확인하고, 답이 없으면 그 항목을 고객용 글에서 제외한다. '모른다·미확인·확인 필요·정보가 서로 다르다'는 수집 상태를 본문·표·캡션·이미지·CTA에 적지 않는다. 내부 사실·전략·검수 기록에는 누락과 충돌을 보존한다. 사진은 보이는 구조의 근거이며 면적·층고·법적 용도·거리의 근거가 아니다.
- **전략 확인.** 사용자에게 추천 전략 한 안을 보여주고 실제 확정 응답을 받기 전에는 최종 원고 작성·이미지 제작·네이버 입력을 시작하지 않는다. 예외는 사무소 상담 배너 하나다 — 매물 내용이 없고 사무소명·연락처만 들어가므로 수집 단계에서 미리 확인·생성해 둘 수 있다. 추천 제목의 방향과 개요까지는 제안할 수 있다. 매물의 핵심 조건 또는 타겟 변경은 재확인한다. 문체만 수정하면 기존 확정을 유지한다.
- **검색어는 추천 후보.** 기본은 실시간 검색 조사 없는 추론이다. 검색량·순위·경쟁도를 만들지 않고 키워드 반복 횟수를 목표로 삼지 않는다.
- **원본과 권한.** 검증된 로컬 원고가 only browser-writing source다. Do not rewrite during transfer. 수정은 로컬 파일부터 한다. Never request credentials. 로그인은 사용자가 내장 브라우저에서 한다. 전용 브라우저의 쿠키·로그인 파일을 복사하지 않는다. task-owned tab 또는 사용자가 지정한 작업 탭을 쓴다.
- **임시저장만.** Never publish. 예약 발행·공개 범위 변경·기존 글 삭제도 하지 않는다. 저장 버튼만 사용한다(현재 UI 명칭 `저장`, 임시저장 동작). 기존 사용자 임시저장 글을 덮어쓰지 않는다. **블로그 화면의 어떤 '삭제' 버튼도 누르지 않는다** — 임시저장 목록의 '전체 삭제'가 '선택 삭제'보다 앞에 있어 클릭 한 번에 저장 글 전부가 지워진다(실사고, 휴지통 없음). 브라우저 확인창은 취소만 누른다.
- **정직한 검수.** 저장 상태 `SAVED / BLOCKED / UNVERIFIED / FAILED`와 완성도 `완료 / 보완 필요 / 확인 불가`를 따로 보고한다. 저장 신호만으로 완료라고 하지 않는다. 실패해도 로컬 원고·사진을 보존한다. 실패를 보고할 때는 명령의 JSON 출력과 오류 문구를 **고치지 않고 그대로** 붙인다. 자기 말로 요약해 대신하지 않는다(Dr-Min 2bb1d26).

## 속도 규칙 (항상 적용)

2026-10-10 실행 분석: 8분 중 대부분이 문서 재독, 소스 코드 열람, JSON 파일을 하나씩 쓰는 왕복, 별도 업로드 동의 질문, 사진별 개별 호출이었다.

0. 모든 기록·메모·보고는 **한국어**로 쓴다(10-10 실행에서 capture 메모가 일본어로 남은 사례).
1. 참조 문서는 해당 단계 시작 때 **한 번만** 읽는다. `scripts/` 소스 코드는 읽지 않는다 — 필요한 값은 명령이 준다(`workflow.mjs office-hash`, `post-template`).
2. 브라우저 작업은 [browser-collect.md](references/browser-collect.md)·[transfer-contract.md](references/transfer-contract.md)의 **빠른 경로 셀**을 그대로 쓴다. 한 동작마다 셀을 나누지 않는다.
3. 서로 의존하지 않는 셸 작업(facts·context·strategy 파일 쓰기, 썸네일·배너 생성)은 한 번에 묶어 실행한다.
4. 사용자에게 묻는 것은 **최대 두 번**이다: ① 원고 전 사실 확인(현장 질문 포함) ② 전략 확정 + 사진·썸네일·배너 업로드 동의. 업로드 동의를 따로 다시 묻지 않는다.
5. `post.json`은 `workflow.mjs post-template --run <경로>`가 만든 뼈대의 TODO만 채운다. 해시·사진 경로·조건표 값·배너 office_hash를 손으로 만들지 않는다.
6. **이미지 생성은 기다리지 않는다.** 이미지 생성은 비동기 셀로 걸고, 끝나기를 기다리는 동안 이미지와 무관한 일을 한다. 2026-10-10 실행에서 확인된 형태:
   - 셀 첫 줄에 `// @exec: {"yield_time_ms": 1000}`를 두고 `const img = await tools.image_gen__imagegen({prompt})` → `store("thumbResult", img)`. 셀은 1초 뒤 돌아오고 생성은 계속된다.
   - 나중에 `wait`(해당 cell_id)로 완료를 확인하고 `load("thumbResult")`로 결과를 읽어 **직접 열어 글자를 확인**한다.
   - **상담 배너:** 재사용할 수 있으면 만들지 않는다. 새로 만들어야 하면 매물 수집 단계(전략 확정 전)에 미리 걸어 둔다.
   - **썸네일:** 전략 확정 응답을 받자마자 건다(확정된 제목·후킹이 필요하다).
   - 썸네일을 기다리는 동안 할 일: `post-template` 실행과 TODO 문장 채우기, 내장 브라우저로 블로그 열기·로그인 확인, 임시저장 목록 확인(중복 방지), 글쓰기 화면 열기.
   - 기다려야 하는 일: `prepare`(이미지 파일과 육안 확인 `reviewed:true`가 필요), 본문 붙여넣기와 업로드(`begin` 이후).

## 1. 입력·프로필·매물 분석

1. `node scripts/profile.mjs`로 기존 사무소 프로필을 읽는다. 기본 위치는 `~/.codex/naver-realtor-blog/profile.yaml`. 기존 필드와 사용자 추가 설정을 유지하고 새로 제공된 사무소 정보만 갱신한다. 기본 CTA는 등록된 `office.public_contact`의 전화 상담이다. 없으면 필요한 정보와 함께 질문한다.
   프로필의 prohibited.claims에 등록된 금지 표현을 전략·이미지·최종 원고에 적용한다.
   사용자가 블로그 주소를 주면 `office.blog_id`에 저장해 다음부터 묻지 않는다. 프로필과 메시지 모두에 블로그 ID가 없으면 사무소 정보와 함께 한 번에 묻는다. 묻는 이유(임시저장할 블로그를 정확히 고르기 위해)와 찾는 법(`blog.naver.com/` 뒤의 영문·숫자)을 같이 알려준다.
2. `node scripts/init-run.mjs --slug <매물명>`으로 새 작업 폴더를 만든다. 기본 위치는 스킬 폴더 밖인 `~/.codex/naver-realtor-blog/runs/`다(스킬 재설치로 작업이 지워지지 않게). 중단 작업이면 새로 만들지 말고 `workflow.mjs status --run <경로>`를 읽는다.
3. 번호·링크 입력은 [input-listing.md](references/input-listing.md)와 [browser-collect.md](references/browser-collect.md)를 따른다. 링크는 `import-listing.mjs resolve`로 번호를 뽑고, 내장 브라우저로 사실과 **갤러리 사진 전체**를 수집한 뒤 `import-listing.mjs import`로 정리한다. 사진 수 `expected/downloaded/failed/duplicates`를 그대로 보고한다. 자연어와 사진도 그대로 받는다. 원문·수집 결과는 보관하고 덮어쓰지 않는다.
4. 사진을 실제로 열어 분류한다. 사진 누락·실패·제외 사유를 기록한다. 사실은 `facts.json`으로 정규화하며 원문 위치와 발췌를 연결한다. 아파트·빌라·오피스텔·주택·상가·사무실·창고·공장·공장·창고·토지를 구분한다.
5. [workflow-contract.md](references/workflow-contract.md)의 형식으로 `workflow.mjs facts --run <경로> --file <facts.json>`을 실행한다. 유형·거래 자체가 불명확하면 그 부분부터 확인한다.
6. 아래 현장 포인트·상담 노하우 절차와 [strategy-guide.md](references/strategy-guide.md)를 따른다. 원고에 필요한 사실 확인과 선택적인 현장 질문을 한 번에 묶어 질문한다. 전략 승인 질문에 미확인 목록을 붙이는 것만으로 사실 확인을 대신하지 않는다.

### 현장 포인트와 사무소 상담 노하우

[broker-knowledge.md](references/broker-knowledge.md)의 분류·저장 계약을 먼저 읽는다. 기본 흐름은 **매물 분석 → 관련 노하우 조회 → 필요한 현장 질문 → 전략 한 안**이다.

- 전략 전에 `knowledge-list --run <경로>`로 같은 사무소 프로필의 적용 가능한 활성 노하우를 읽는다. 다른 프로필을 쓰면 모든 관련 명령에 동일한 `--profile <profile.yaml>`을 전달한다. 유형·지역·거래 조건이 맞지 않거나 적용 범위가 불명확한 노하우는 쓰지 않는다.
- 추천 이유나 실제 고객 반응이 이미 충분하면 다시 묻지 않는다. 부족할 때만 해당 매물에 맞는 “비슷한 매물보다 추천하는 점”, “고객이 좋아하거나 망설인 부분” 중 필요한 질문을 **최대 2개, 한 묶음으로 한 번만** 묻는다. 이미 답한 내용이나 노하우에 있는 상담 우선순위를 재질문하지 않는다. 기존 가격·면적 확인 및 노하우 충돌 질문과 함께 묶는다.
- `broker-context.json`에 판단 이유, 질문 여부, 실제 사용자 발언과 **매물 사실 / 중개사 평가 / 전달받은 고객 반응**을 구분해 `context-save`한다. 확인된 매물 사실만 사용자 출처와 연결해 facts에 반영한다. 평가·반응을 객관적 우수성·보편적 수요·가짜 후기·방문 경험으로 쓰지 않는다.
- 답변을 기다릴 기회를 주고, 답이 없거나 건너뛰면 `unanswered` 또는 `skipped`로 기록한 후 추가 현장 질문 없이 확보된 사실로 추천한다. 유형·거래 등 필수 사실은 기존대로 확인한다. 미응답 조건과 수집 상태는 고객용 글에서 제외한다.
- “우리 창고 고객들은 차량 진입을 먼저 물어본다”처럼 **반복 적용 의도가 명확한 사용자 설명만** `knowledge-save`로 자동 저장하고 “사무소 상담 노하우로 기억했습니다: …”라고 짧게 알린다. 별도 저장 승인 질문은 하지 않는다. “이 창고를 본 고객이 좋아했다”는 해당 작업의 현장 기록에만 남긴다. 고객 이름·연락처를 제거하며 AI의 타겟 가설은 저장하지 않는다.
- 같은 내용은 중복 저장하지 않는다. 명시적 수정은 기존 항목을 대체하고, “이건 잊어줘”는 `knowledge-retire`로 비활성화한다. 해석이 모호한 충돌은 양쪽 적용을 보류하고 기존 질문 묶음에서 확인한다. 답이 없으면 보류를 유지한다.
- 현장 포인트와 노하우는 타겟·후킹·질문·설명 순서/깊이·CTA를 설계하는 참고다. **상담 노하우를 해당 매물의 주차·진입·가격·설비 사실의 근거로 쓰지 않는다.** 사용한 식별자·내용 스냅샷·활용 이유를 전략의 선택 항목 `context_refs`와 `knowledge_refs`에 남긴다.

## 2. 추천 전략 한 안 → 사용자 확정

`strategy.json`을 작성하고 `workflow.mjs propose --run <경로> --file <strategy.json>`으로 검증한다. 다음 여덟 행으로 사용자에게 보여준다.

| 항목 | 내용 |
|---|---|
| 매물 해석 | 유형·거래 방식·확인된 핵심 조건 |
| 주 타겟 | 이용 목적·우선 조건·선정 근거, 추론임을 구분 |
| 검색 의도 | 검색으로 해결하려는 구체적인 질문 |
| 검색어 후보 | **추천 후보**인 중심 표현 1개 + 관련 표현 2~4개 |
| 후킹 | 확인된 조건이 타겟에게 주는 가치 |
| 콘텐츠 구성 | 제목 방향·도입·문단별 질문/근거/사진 |
| 문의 유도 | 문의로 확인하거나 안내받을 내용 + 등록 연락 수단 |
| 확인 사항 | 미확인·충돌 정보와 원고에서 제외할 주장 |

표 아래에 **제외한 사실 목록**을 붙인다(`사실 | 이유`). 사용하는 사실은 "나머지 N개는 본문·표에 사용"으로 한 줄만 적는다. 판단은 확인된 사실 전부에 대해 하고, 전부를 `strategy.json`의 `fact_coverage`에 기록하며 `propose`가 누락을 검사한다. 이유 없이 사실을 빼지 않는다(2026-10-09 파주 테스트에서 대지·전력·사용승인 등이 이유 기록 없이 빠졌다). 사용자가 "그것도 넣어"라고 하면 반영해 다시 제안한다.

노하우를 사용한 관련 행에 **“사무소 상담 경험 반영”**을 짧게 표시하며 위 여덟 행은 유지한다. 이 표시는 사용자에게 보여주는 전략 설명이며 고객용 광고의 후기 문구가 아니다.
새 노하우 저장이나 현장 기록 추가만으로 이미 확정한 전략을 자동 변경하지 않는다. 현재 글의 타겟·후킹·주요 구성이 달라질 때 수정 전략을 제시해 다시 확인받는다. 단순 문체 수정은 기존 확정을 유지한다.

확정 질문에는 업로드 동의를 함께 넣는다: "이 전략으로 진행하고, 사진 N장·썸네일·상담 배너를 네이버 블로그 <ID>의 새 임시저장 글에 업로드해도 될까요?" 응답은 approval.json의 user_quote와 upload_consent에 그대로 남긴다.

사용자 수정은 반영해 다시 제안한다. 명확한 확정 응답을 받으면 해당 시점의 listing_hash, strategy_hash와 실제 응답을 `approval.json`에 기록하고 `workflow.mjs approve`를 실행한다. 실행 계획에 대한 과거 동의나 단순 침묵을 매물 전략의 확정으로 간주하지 않는다.

## 3. 문체 적용·콘텐츠 제작

`workflow.mjs check-approved --run <경로>`를 먼저 통과한다. 다음 순서를 바꾸지 않는다.

1. `workflow.mjs style-get --blog <ID/URL>`로 해당 블로그의 저장 문체를 확인한다. 사용자가 직접 정한 말투·형식이 저장 문체나 기존 글 분석보다 우선한다.
2. 없으면 기존 블로그 주소를 받는다(이미 주어진 주소는 재질문하지 않는다). 공개된 **매물 글 최대 5개**의 실제 본문을 **내장 브라우저로 열어** 읽고 문체를 추출한다. 웹 검색·셸 다운로드(curl 등)로 본문을 가져오지 않는다.
3. 기존 블로그가 없거나 본문을 못 읽으면 타겟에 맞는 기본 문체로 진행하고 이유를 남긴다. 한두 편만 읽었다면 표본 부족을 표시한다.

존댓말·문장 길이·문단 리듬·도입·소제목·전문용어 설명·강조·이모지·상담 표현을 저장한다. 글 주소·분석 시점·짧은 본문 근거를 보관한다. 기존 글의 매물 사실·경험·후기 문장을 새 글로 옮기지 않는다. 사용자가 변경을 요청할 때만 실제 요청문을 기록하고 저장 스타일을 갱신한다. 사용자 수정 사항과 충돌하는 과거 말투·리듬은 재사용하지 않는다.

**기본 말투와 네이버 배치:** 매물을 잘 이해한 중개사가 고객에게 편하게 설명하는 친숙한 존댓말을 쓴다. 쉬운 단어와 짧은 문장으로 직접 설명한다. 확인된 사실을 매번 '확인할 수 있습니다·보입니다·표시됩니다·등록사진'으로 돌려 말하지 않는다. 방문하지 않았다면 방문한 경험을 만들지 않는다. 본문은 한 문장당 한 paragraph 블록, 문장 사이 정확히 빈 줄 한 줄, 모든 문장은 가운데 정렬한다. 소제목·사진 설명·표 안의 글·상담 문구·연락처도 가운데 정렬한다. 자세한 예시와 예외는 [content-format.md](references/content-format.md)를 따른다.

`workflow.mjs post-template --run <경로>`로 `post-template.json`을 만들고 TODO를 채워 `post.json`으로 저장한다(사진은 이미 전부 배치돼 있다; 뺄 사진만 블록을 지우고 excluded_photos에 이유를 적는다). [content-format.md](references/content-format.md)에 따라 사진·썸네일·상담 배너를 만든다. 제목부터 CTA까지 확정된 검색 의도를 일관되게 설명한다. 썸네일·배너 제작은 현재 환경에서 제공되는 이미지 제작 기능을 사용한다. 배너의 사무소명·연락처를 실제로 읽어 현재 프로필과 대조하고 바뀌면 새로 만든다.

`workflow.mjs prepare --run <경로> --file <post.json> --blog <ID>`가 원고·HTML·컴포넌트 목록을 생성한다. `node scripts/validate-draft.mjs --file <run>/blog-post.md`를 실행해 오류를 수정한다. 숫자·근거 연결 검사는 코드가 하고, 거리·수익·용도·사진 해석 등 의미가 근거에서 실제로 도출되는지는 Codex가 검수한다. 코드 통과만으로 사실 검수를 대체하지 않는다.

## 4. 내장 브라우저 입력·임시저장·재열람

[transfer-contract.md](references/transfer-contract.md)를 읽는다. `workflow.mjs begin --run <경로>` 통과 후 제공되는 내장 브라우저 API만으로 편집기에 입력한다. 본문 일괄 붙여넣기(딱 한 번) → 텍스트 전화 링크(**반드시 사진보다 먼저**, 이미지에 링크 레이어를 쓴 뒤에는 텍스트 링크가 줄을 지운다) → 사진·지도 자리 교체 → 남은 `@@IMG/MAP@@` 확인 → 저장 전 확인 → 저장 → **동일 임시저장 글 재열람** 순서다.

사진은 `tab.playwright.waitForEvent("filechooser")`를 먼저 걸고 '사진 추가'를 누른 뒤 `chooser.setFiles([절대경로])`로 올린다. 파일 업로드는 Browser 플러그인 확인 정책상 사전 승인 항목이므로, 전략 확정 때 업로드할 파일과 목적지(네이버 블로그 임시저장 글)에 대한 동의를 함께 받아 기록한다.

저장과 검증은 [transfer-contract.md](references/transfer-contract.md) '저장·재열람'의 셀 A(저장+임시저장 개수) → **중간 보고** → 셀 B(새 탭에서 같은 글을 열어 관측 파일 작성) → `workflow.mjs verify --run <경로> --file <run>/reopened-observation.json` 순서다. 비교는 코드가 한다(제목·모든 문장·자리 표시·굵게 번짐·사진·표 셀과 테두리·지도·전화 링크). 저장이 애매하거나 이전 시도가 있으면 먼저 임시저장 목록에서 제목·시각·식별자를 확인하고 `workflow.mjs reconcile`을 실행한다. 기존 글을 찾았으면 그 글에서 재개하며 새 글을 만들지 않는다.

**보고는 두 번 한다.**
1. 중간 보고 — 임시저장 개수가 늘어난 것을 보자마자: "임시저장했어요(목록 N→N+1개). 지금 저장된 글을 다시 열어 검증하고 있어요." 이때는 '완료'·'SAVED'라고 하지 않는다.
2. 최종 보고 — verify가 끝나면: "검증이 끝났어요." + 저장 상태·완성도 + 실패/unknown 항목.

최종 보고: 전략 요약, 저장 상태, 완성도, 임시저장 글의 제목/식별자, 원고·이미지 경로, 누락/실패/확인 불가 항목. 실제 검색 유입과 문의 증가는 발행 후 확인할 사업 성과로 구분한다.

## 설치·유지보수

Node.js **20 이상**. 모든 스크립트는 Node 내장 모듈만 사용한다. **`npm install`·`npm ci`가 필요 없다** — 스킬 폴더를 복사하면 설치가 끝난다. Codex 앱의 Browser 플러그인(내장 브라우저)이 켜져 있어야 한다.

수정 후 `node scripts/check-core.mjs`, 저장소 루트의 `npm test`, skill-creator의 `quick_validate.py`를 실행한다. 유형별 수동 검증 기준은 [evaluation-cases.md](references/evaluation-cases.md)를 따른다.
